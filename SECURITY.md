# Security Policy

Report security issues privately through a GitHub Security Advisory in this repository; do not publish exploitable details in public issues.

## Supported Versions

ThunderLoad is pre-1.0 and under active development. Only the latest release (currently 0.3.5) receives security fixes; earlier releases are not supported.

## Security Design
- **100% local architecture:** ThunderLoad has no remote telemetry, analytics, or cloud backend. All media detection, session handoff, and download orchestration happen locally on the user's device. The extension itself loads no remote code — all of its JavaScript ships inside the submitted package. One exception, by explicit user action only: the desktop app or the extension can download the yt-dlp and Deno executables on demand from GitHub Releases (yt-dlp 2026.10.26 from `github.com/yt-dlp/yt-dlp/releases`, Deno 2.9.8 from `github.com/denoland/deno/releases`), only when the user clicks the Download button for that tool. A first install is SHA256-verified against a pinned hash before it is used. Updating yt-dlp is different: it downloads and installs the latest release unpinned, via `yt-dlp -U`, after asking for confirmation. The new binary's own hash is then recorded and used as tamper-evidence on later launches — not a pinned-release guarantee. Nothing else is fetched or executed from a remote source.
- **Scoped automatic detection:** The extension requests `<all_urls>` host permission, `webRequest` (and `webRequestBlocking` on Firefox only), and injects `content.js` (`document_idle`) and `hook.js` (`MAIN` world, `document_start`) to detect playable media automatically. Detected URLs and the intercept retry queue are stored locally in `chrome.storage.local` and never leave the device.
- **Authenticated session handoff:** The `cookies` permission is used solely to pass origin-matched cookies over the local `nativeMessaging` pipe to the user-installed native host when inspecting or downloading authenticated media. The native host validates session origins before use, writes job state files with `0o600` permissions on Unix, and keeps the `"session"` credentials in `.native-jobs/<id>.json` on `Interrupted`, `Failed`, and `Paused` — a paused or failed job still needs its session to resume or retry. The session is scrubbed from the state file only when the job reaches `Completed` or `Cancelled`, or when the job is successfully handed over to the desktop engine (the native state file is then deleted and the session lives only in the desktop job database).
- **Optional native messaging:** `nativeMessaging` is declared under `optional_permissions` and requires explicit user consent and a separately installed local native host.
- **Filename & path sanitization:** Download and subtitle filenames are sanitized in both the extension and native host (stripping path separators, reserved characters, and ASCII control characters, and capping stem length) before writing to the user's download directory.
- **Scope boundary:** DRM circumvention and access-control bypass are out of scope.
